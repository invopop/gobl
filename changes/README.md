# Changes

Release notes are kept as individual files so that pull requests never edit the
same lines of the same file. [CHANGELOG.md](../CHANGELOG.md) is generated from
this directory and must not be edited by hand.

- **unreleased**: one file per pull request, describing the changes it makes.
- **releases**: the notes published with each version.
- **HEADER.md**: the introduction to the generated changelog.

The tooling lives in [pkg/changes](../pkg/changes), and is not specific to
GOBL: any project laying its notes out this way can use it.

## Describing a change

Add a file to `changes/unreleased` named after your branch, for example
`changes/unreleased/bill-round-to-currency.md`. A branch name containing a
slash, such as `fix/rounding`, may keep it: subdirectories are read too.

```markdown
## Added

- `bill`: `RoundToCurrency` recalculates an invoice so that every amount fits
  the currency's precision.

## Fixed

- `bill`: `RemoveIncludedTaxes` no longer panics on documents that have not
  been calculated.
```

Guidelines:

- Group entries under `## Added`, `## Changed`, `## Deprecated`, `## Removed`,
  `## Fixed`, or `## Security`. Any other heading is rejected.
- Only include the sections you need, in any order.
- Prefix each entry with the package, regime, addon, or catalogue key it
  affects, as in `` `bill`: `` or `` `gr-mydata-v1`: ``.
- Describe what the change means for someone using GOBL, and mark anything that
  breaks an existing document or API with **breaking**.
- Don't add a title: the headings are nested a level deeper when they reach the
  changelog. Text before the first heading is kept as an introduction to the
  release, so use it only for changes that warrant one.

Run `mage changes:preview` to see the release notes your file will produce
alongside everything else that is pending.

## Publishing a release

1. Create a branch from `main` named after the version, such as
   `release-0.506.0`.
2. Bump `VERSION` in [version.go](../version.go).
3. Run `mage changes:release`.
4. Commit the result as `Release 0.506.0` and open a pull request against
   `main`.

`mage changes:release` merges every pending file into a single dated release
note, such as `changes/releases/2026-09-14-v0.506.0.md`, and regenerates
`CHANGELOG.md`. Merging the pull request changes `version.go` on `main`, which
tags the version and publishes the GitHub release.

### Choosing the version

GOBL versions are `v0.X.Y`:

- **Minor** (`v0.506.0` → `v0.507.0`): regular releases, including those with
  breaking changes, which the release notes mark with **breaking**.
- **Patch** (`v0.506.0` → `v0.506.1`): small follow-ups to the latest release,
  such as fixes or minor additions that should be available without waiting
  for the next regular release.
- **Hundreds** (`v0.400.0` → `v0.500.0`): major changes to the GOBL models,
  which may be published first as release candidates, such as `v0.400.0-rc1`.

If you edit a release note or `HEADER.md` afterwards, run `mage changes:format`
to restore the canonical form of the notes; the changelog is regenerated by the
next `mage changes:release`.
